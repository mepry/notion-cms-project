# ROADMAP: 노션 포트폴리오

[PRD](PRD.md)를 기준으로 한 개발 로드맵입니다. 1인 개발, 하루 4~6시간 작업을 기준으로 시간을 잡았습니다.

## 한눈에 보기

| 단계 | 이름                    | 주요 결과물                               | 예상 기간   |
| ---- | ----------------------- | ----------------------------------------- | ----------- |
| 1    | 프로젝트 초기 설정      | 실행되는 앱 골격, Notion 연결 확인        | 1일         |
| 2    | 공통 모듈/컴포넌트 개발 | Notion 데이터 계층, 타입, 레이아웃, UI    | 2일         |
| 3    | 핵심 기능 개발          | 글 목록, 글 상세(블록 렌더링)             | 3~4일       |
| 4    | 추가 기능 개발          | 필터, 검색, 작성 기록 잔디, 카테고리 화면 | 3~4일       |
| 5    | 최적화 및 배포          | 캐시, SEO, 반응형 점검, 배포              | 2일         |

## 1단계. 프로젝트 초기 설정 (골격 구축)

**예상 기간:** 1일

### 할 작업

- [ ] PRD의 열린 질문 결정
  - Next.js 버전 (15 / 기존 Starter Kit의 16)
  - 글 URL 방식 (Notion 페이지 ID / `Slug` 속성 추가)
- [ ] 기존 Starter Kit에서 포트폴리오에 필요 없는 기능(로그인, 게시판, 관리자, Prisma, Redis) 정리 범위 결정
- [ ] `@notionhq/client` 설치
- [ ] 환경 변수 설정: `.env`, `.env.example`에 `NOTION_TOKEN`, `NOTION_DATABASE_ID` 추가
- [ ] Notion 데이터베이스 생성 (PRD 6장 구조: Title, Category, Tags, Published, Status, Content)
- [ ] Notion Integration 생성 후 데이터베이스에 연결
- [ ] 샘플 글 5개 작성 (초안 1개 포함, 카테고리·날짜를 섞어서)
- [ ] 라우트 골격 생성: `/`, `/posts/[slug]`, `/categories/[category]` (빈 페이지)

### 왜 이 순서인가

Next.js 버전이나 URL 방식처럼 **나중에 바꾸면 전체를 고쳐야 하는 결정**을 먼저 끝내야 합니다. 또 실제 Notion 데이터가 있어야 이후 단계에서 진짜 응답 구조를 보고 개발할 수 있습니다.

### 완료 기준

- `npm run dev`로 세 경로가 모두 열린다.
- 서버에서 Notion 데이터베이스를 조회하면 샘플 글 5개가 응답으로 온다.
- `npm run build`, `npm run lint`가 통과한다.

## 2단계. 공통 모듈/컴포넌트 개발

**예상 기간:** 2일

### 할 작업

**데이터 계층 (`lib/notion/`)**

- [ ] Notion 클라이언트 초기화 유틸 (서버 전용)
- [ ] `Post` 타입 정의: `id`, `slug`, `title`, `category`, `tags`, `published`, `status`
- [ ] Notion 응답 → `Post` 변환 함수 (속성 파싱)
- [ ] `getPublishedPosts()`: `Status = 발행됨` 필터, `Published` 내림차순, `next_cursor` 페이지네이션 처리
- [ ] `getPostBySlug()`, `getPostBlocks()` (하위 블록 재귀 조회)
- [ ] 오류 처리와 로깅 (기존 `apps/web/src/lib/logger.ts` 재사용)

**UI 컴포넌트**

- [ ] 레이아웃: 헤더(로고, 카테고리 메뉴, 검색 자리), 푸터
- [ ] 글 카드 `PostCard` (제목, 카테고리, 태그, 발행일)
- [ ] 카테고리 배지, 태그 배지 (기존 `components/ui/badge.tsx` 재사용)
- [ ] 빈 상태 `EmptyState`, 로딩 스켈레톤, 404 페이지
- [ ] 날짜 포맷 유틸

**테스트**

- [ ] 속성 파싱·필터·정렬 함수 단위 테스트

### 왜 이 순서인가

목록, 상세, 필터, 검색, 잔디는 **모두 같은 데이터(`Post` 목록)와 같은 카드·배지**를 씁니다. 공통 부분을 먼저 만들어 두면 기능마다 Notion 호출 코드를 중복해서 짜지 않아도 되고, Notion API가 바뀌어도 한 곳만 고치면 됩니다.

### 완료 기준

- `getPublishedPosts()`가 발행된 글만 최신순으로 반환한다 (초안은 제외).
- 공통 컴포넌트가 샘플 데이터로 화면에 표시된다.
- 변환·필터 함수 단위 테스트가 `npm run test`로 통과한다.

## 3단계. 핵심 기능 개발

**예상 기간:** 3~4일

### 할 작업

**글 목록 (홈 `/`)**

- [ ] 최근 글 카드 목록 (반응형 그리드: 모바일 1열 / 태블릿 2열 / 데스크톱 3열)

**글 상세 (`/posts/[slug]`)**

- [ ] 메타 정보: 카테고리, 발행일, 태그
- [ ] Notion 블록 렌더러
  - 제목(heading 1~3), 문단, 글머리/번호 목록, 할 일 목록
  - 코드(구문 강조), 인용, 콜아웃, 구분선
  - 이미지, 북마크/링크, 토글
  - 리치 텍스트 서식: 굵게, 기울임, 취소선, 인라인 코드, 링크, 색상
- [ ] 지원하지 않는 블록은 건너뛰기 (화면이 깨지지 않게)
- [ ] 이전 / 다음 글 링크
- [ ] 없는 글이거나 초안이면 404

### 왜 이 순서인가

**"Notion 글을 사이트에서 읽을 수 있다"가 이 서비스의 존재 이유이자 MVP의 P0**입니다. 필터·검색·잔디는 글 목록이 있어야 의미가 있으므로, 핵심 흐름(목록 → 상세)을 먼저 끝내 두면 이 시점에 이미 최소한으로 쓸 수 있는 사이트가 됩니다.

### 완료 기준

- 홈에서 발행된 글이 최신순으로 보이고, 클릭하면 상세 페이지로 이동한다.
- 샘플 글에 들어간 모든 블록 종류가 깨지지 않고 표시된다.
- Notion에서 `Status`를 `초안`으로 바꾼 글은 목록과 상세 모두에서 보이지 않는다.

## 4단계. 추가 기능 개발

**예상 기간:** 3~4일

### 할 작업

**카테고리·날짜 필터 (F2)**

- [ ] 카테고리 페이지 `/categories/[category]`
- [ ] 카테고리 칩 (전체 + 카테고리 목록)
- [ ] 연도 / 월 필터
- [ ] 필터 상태를 URL 쿼리 파라미터로 유지 (`?year=2026&month=10`)

**검색 (F3)**

- [ ] 헤더 검색창 (`?q=`)
- [ ] 제목·태그 대상, 대소문자 구분 없이 검색
- [ ] 결과 없음 안내 (공통 `EmptyState` 재사용)

**작성 기록 잔디 (F4)**

- [ ] 발행일 기준 일별 글 수 집계 함수 + 단위 테스트
- [ ] 53주 × 7일 그리드, 글 수별 색 단계 (0 / 1 / 2 / 3+)
- [ ] 툴팁 (`2026-10-20 · 글 2개`), 모바일은 탭으로 표시
- [ ] 셀 클릭 시 그 날짜의 글 목록으로 이동
- [ ] 모바일 가로 스크롤

### 왜 이 순서인가

세 기능은 모두 **3단계에서 만든 글 목록을 거르거나 집계하는 기능**입니다. 목록이 먼저 안정돼야 그 위에 얹을 수 있고, 서로 의존하지 않아 어떤 것부터 해도 됩니다. 탐색에 가장 많이 쓰이는 필터 → 검색 → 잔디 순서를 추천합니다.

### 완료 기준

- 카테고리·연도·월 필터와 검색을 조합해도 올바른 글만 보인다.
- 필터가 걸린 URL을 새로고침하거나 공유해도 같은 결과가 나온다.
- 잔디 셀 수가 실제 발행일별 글 수와 일치한다.

## 5단계. 최적화 및 배포

**예상 기간:** 2일

### 할 작업

**성능**

- [ ] ISR(`revalidate`)로 페이지 캐시. Notion 이미지 URL이 약 1시간 뒤 만료되므로 주기를 1시간 미만으로 설정
- [ ] 목록은 한 번 가져와 캐시하고 필터·검색은 캐시된 데이터로 처리 (Notion 요청 제한: 평균 초당 3회)
- [ ] `next/image`로 이미지 최적화, 폰트 최적화

**품질**

- [ ] 반응형 점검 (모바일 < 640px / 태블릿 640~1024px / 데스크톱 > 1024px)
- [ ] 접근성 점검: 시맨틱 태그, 이미지 대체 텍스트, 키보드 탐색, 색 대비
- [ ] SEO: 페이지별 `metadata`, OG 이미지, `sitemap.xml`, `robots.txt`
- [ ] E2E 테스트: 목록 → 상세 이동, 필터, 검색 (Playwright)

**배포**

- [ ] 배포 플랫폼에 환경 변수(`NOTION_TOKEN`, `NOTION_DATABASE_ID`) 등록
- [ ] 프로덕션 배포 및 도메인 연결
- [ ] README에 배포 주소와 실행 방법 추가

### 왜 이 순서인가

기능이 다 갖춰진 뒤에 최적화해야 **실제 병목을 측정하고 고칠 수 있습니다.** 기능을 만드는 도중에 최적화하면 바뀔 코드에 시간을 쓰게 됩니다. 배포는 모든 점검이 끝난 마지막 단계입니다.

### 완료 기준

- Lighthouse Performance 90점 이상, 캐시된 페이지 LCP 2.5초 이하
- Notion에서 글을 발행하면 재검증 주기 안에 사이트에 반영된다.
- `npm run build`, `npm run lint`, `npm run test`, E2E 테스트가 모두 통과한다.
- 배포 주소에서 세 화면이 모바일·데스크톱 모두 정상 동작한다.

## MVP 체크포인트

PRD의 MVP 범위는 **3단계 완료 + 5단계 반응형 점검**으로 충족됩니다. 일정이 빠듯하면 4단계 일부를 미루고 먼저 배포할 수 있습니다.

| MVP 항목               | 완료 단계         |
| ---------------------- | ----------------- |
| Notion API 연동        | 1~2단계           |
| 글 목록 및 상세 페이지 | 3단계             |
| 기본 스타일링          | 2~3단계           |
| 반응형 디자인          | 3단계, 5단계 점검 |

## 이후 (MVP 이후)

PRD 13장 참고: 본문 전문 검색, 태그 페이지, RSS, 다크모드 토글, 조회수, Notion Webhook으로 발행 즉시 캐시 무효화.
